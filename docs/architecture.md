## 0. 重新核对：StellarAlia 的渲染器能不能上板子

所以早先的结论（不移植 StellarAlia 的渲染器，新写运行时，复用它的数据和非渲染系统）仍然成立。

## 1. 目标和不做的事

**目标**

1. **帧预算**：主路径 60 fps（屏幕约 66 Hz，按固定步长逻辑加插值渲染来适配）；重场景允许 30 fps。每帧 CPU 预算约 8 ms（4 核 A53），GPU 预算以 E2 阶段实测为准，初始目标是 640×360 下 5 万三角形。
2. **省带宽**：内存带宽约 2 GB/s，是最紧的资源。规则：
   - 场景按 **640×360** 内部分辨率渲染，最后一个 pass 整数倍放大到 1280×720（电视 1080p 是 3 倍）；
   - 每个渲染目标只开一次 pass，开始时 clear、结束时丢弃深度（tile GPU 的规矩）；
   - 旋转、调色、抖动、HUD 都合并进最后一个 pass；
   - 不做全屏透明叠加，不做帧中回读。
3. **同一份代码跑 PC 和板子**：PC（Arch，Mesa 也能提供 GLES 上下文）就是模拟器的渲染端，着色器和 API 与板上完全一样。
4. **玩法开发要快**：Megalith 的 Python 玩法代码不改就能跑；新游戏可以用 Python 写玩法，热点下沉到 C++。
5. **能被嵌入**（E5，以后）：宿主应用可以把引擎渲染的 3D 画面当成一个控件，所以引擎既能独立运行，也能画进宿主给的帧缓冲。

**不做的事（至少第一版不做）**

- 延迟渲染、PBR、IBL、实时阴影图、后处理链（这些正是 StellarAlia 在板上跑不动的部分）；
- 在设备上运行 C# 或 Roslyn；
- 在设备上做资源导入：所有资源在 PC 上烘焙好，设备只读烘焙格式；
- 设备上的编辑器；
- 多线程渲染（先单线程渲染加一个异步加载线程，实测有需要再说）。

## 2. 分层

依赖只能**从上往下**，下层不知道上层的存在。每层是一个独立的静态库，有自己的单元测试。

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L8 游戏 / 卡带     Megalith（Python）· 示例游戏 · 以后的 StellarAlia 导出场景   │
├──────────────────────────────────────────────────────────────────────────┤
│ L7 绑定           alia_engine Python 模块（nanobind）· C ABI · g3d 兼容层        │
├──────────────────────────────────────────────────────────────────────────┤
│ L6 运行时         主循环（固定步长 + 插值）· 场景 API · 卡带入口 · 系统集成        │
│                  （暂停/挂起、存档、振动、语言）                                 │
├──────────────────────────────────────────────────────────────────────────┤
│ L5 世界           ECS（EnTT）· 变换层级 · 动画（刚体 rig → 蒙皮）· 碰撞/物理 ·    │
│                  输入动作映射 · 音频混音器                                       │
├──────────────────────────────────────────────────────────────────────────┤
│ L4 资源           烘焙格式读取 · 资源包 / VFS（挂载 .acart）· 异步加载 · 句柄      │
├──────────────────────────────────────────────────────────────────────────┤
│ L3 渲染           掌机渲染管线 · 材质（调色板 / 顶点光照 / ETC2 纹理）· 雾和 Look  │
│                  · 精灵和文字批处理 · 最终 pass（放大、旋转、调色、HUD）· 预算计数 │
├──────────────────────────────────────────────────────────────────────────┤
│ L2 RHI            薄抽象：buffer / texture / render target / pipeline / pass     │
│                  后端：GLES 3.0（主路径）；接口留出 Vulkan 1.0 后端的余地         │
├──────────────────────────────────────────────────────────────────────────┤
│ L1 平台           窗口和表面（SDL3：Wayland / X11）· 无窗口 EGL（surfaceless，   │
│                  基准和 CI）· 宿主模式（画进外部 FBO）· 手柄 / 体感 · 音频设备 · 时钟│
├──────────────────────────────────────────────────────────────────────────┤
│ L0 基础           数学（glm）· 日志 · 性能计数 · 文件 · 内存工具                   │
└──────────────────────────────────────────────────────────────────────────┘
```

各层的边界（谁拥有什么、对外暴露什么）：

| 层 | 拥有 | 对上暴露 | 明确不碰 |
|---|---|---|---|
| L0 基础 | 无状态工具 | 函数和小类型 | 任何平台 API |
| L1 平台 | 窗口、GL 上下文、输入设备、音频设备 | `Surface`（尺寸、方向、交换）、`InputSnapshot`（手柄按键/轴、体感、触摸）、`AudioDevice`（回调） | 渲染概念 |
| L2 RHI | GPU 对象的生命周期 | 句柄 + 命令接口：`createBuffer/Texture/RenderTarget/Pipeline`、`beginPass(loadOp, storeOp)`、`draw` | 场景、材质的含义 |
| L3 渲染 | 帧图（固定的几个 pass）、着色器、GPU 侧网格和纹理缓存 | `submit(DrawList)`：相机 + 不透明物体列表 + 天空 + 雾 + HUD；`stats()` | ECS、文件格式 |
| L4 资源 | 资源包、解码、缓存 | `Handle<Mesh/Texture/Rig/Clip/Sound>`，异步 `load()` | GPU API（只交给 L3 上传） |
| L5 世界 | 实体和组件、各系统的每帧更新 | 组件类型、系统函数；每帧产出一份 DrawList 交给 L3 | 窗口、GL |
| L6 运行时 | 主循环、时间、生命周期 | `Game` 接口（`init / fixed_update / update / shutdown`）、卡带启动 | 具体游戏 |
| L7 绑定 | 语言桥 | Python 模块、C ABI | 引擎内部数据结构（只暴露批量接口） |

**为什么 L3 渲染接受 DrawList，而不是直接读 ECS**：Megalith 的 g3d 帧（相机 + ≤9 个物体 + rig + HUD）本来就是一份"绘制列表"。让渲染层只吃绘制列表，g3d 兼容层（L7）和 ECS（L5）就是两个平级的生产者，Megalith 不用先迁到 ECS 就能跑。

**实际做法（2026-10-28，E1）：不做 g3d 兼容层。**Megalith 的 Python 已经有 rig 姿态求值（`rig.py`）和全部场景数据，所以游戏这边的 `alia_view.py` 直接把每帧的 g3d `Frame` 翻译成引擎的绘制列表（相机、雾、灯、网格实例、HUD）。引擎里没有任何 Megalith 专用的代码，E1 测的就是以后所有游戏都用的通用 API（`alia_engine.Engine`：`create_mesh` / `draw` / `hud_text` / `end_frame`）。g3d 协议只在游戏里当数据结构用。

### 2.1 游戏、运行时和渲染表面的分工（2026-10-29）

**游戏不写渲染表面和主循环的代码。**游戏只描述"要什么"，"怎么显示"由平台和运行时决定，所以同一个卡带不改一行，就能在 PC 窗口、无窗口测试、板上的 sway 和以后的 DSI 竖屏上运行：

| 参数 | 由谁决定 |
|---|---|
| 内部分辨率 | 卡带清单的 `[display] render`（例如 `"640x360"`、`"480x320"`） |
| 输出尺寸、旋转、刷新率 | **合成器**（2026-10-29 定，系统不为此设任何环境变量）。尺寸用全屏 xdg_toplevel 的 configure，SDL 报告为窗口尺寸（sway 把每个卡带都设成全屏）；节奏靠 vsync 和帧回调（swap interval 1），不靠刷新率数字；旋转从 wl_output 的 transform 读，最终 pass 预先转好，再对 SDL 的 wl_surface（`SDL_PROP_WINDOW_WAYLAND_SURFACE_POINTER`）调用 `wl_surface_set_buffer_transform` 设成同样的值，sway 就能直接扫描输出（不设也是对的，只是 sway 要多合成一次）。PC 上就是窗口；调试用的覆盖（例如 `ALIA_DISPLAY_SIZE`）只在引擎这边，系统不设 |
| 无窗口、截图、跑 N 帧、性能统计、输入日志 | 开发和测试用的运行时选项（环境变量或通用命令行参数），对所有游戏都一样 |
| 主循环 | L6 运行时：固定步长、计时、`SIGTERM` 退出。游戏实现 `init / fixed_update(dt) / render(alpha) / shutdown` |
| 物体、相机、灯光、骨骼动画、碰撞 | L5 世界（E4）：游戏创建常驻对象、改变化的部分，引擎每帧渲染；骨骼姿态和碰撞体也由引擎计算 |

L3 的绘制列表（`draw(mesh, model)`、`hud_*`）仍然保留：它是 L5 场景每帧转成的内部接口，有特殊需求的游戏也可以直接用。

E1 的 Megalith 是在这些层出现之前写的。E3a 以后它的 `main.py` 只剩一个 `Game` 类（`alia_engine.run` 管主循环和表面）；`alia_view.py` 自己把每帧的数据翻译成绘制列表、rig 姿态和碰撞在游戏的 Python 里算，这些由 E4 挪进引擎（§6）。

**插值（E4 第 3 步已实现，`api.md` §3）**：逻辑是固定 60 步/秒，显示跟着合成器（板上的无头 sway 约 62.5 Hz：wlroots 的 headless 后端按整毫秒定时，16 ms 一帧，模式虽然设成 60 Hz 也一样，测试环境的特性，不针对它调；DSI 屏按 vblank，约 66 Hz），所以有的帧没有新的逻辑步，画面会重复上一帧（62 Hz 时约每 30 帧一次，66 Hz 时约每 11 帧一次）。`render(alpha)` 已经把"到下一步走了多少"交给游戏，但插值需要常驻的物体状态（上一步和这一步），所以由 E4 的世界层统一做。

## 4. 和系统的对接

引擎只用 Alia Pad 系统的公开接口：标准手柄、环境变量、卡带格式、合成器。卡带格式和环境变量以 Alia Pad 的卡带文档（devkit）为准。

| 系统部分 | 对接方式 |
|---|---|
| 输入 | L1 用 SDL3 的 Gamepad API 读系统提供的手柄。按键按位置命名（South、East……；Alia Pad 上 A = East、B = South）。体感等 IMU 硬件（E3b）。PC 上键盘映射成手柄 |
| `.acart` 卡带 | **不做启动器 `alia-run`**（§5 第 9 项）：读清单、挂载、沙箱、环境变量、生命周期都是系统的事。Python 游戏就是 `runtime.type = "python"` 的卡带，`entry = "main.py"`，由系统的 python3 运行；引擎是扩展模块 `alia_engine`（`.so`，不链接 libpython），随卡带放在 `content/python/`，版本跟着游戏走。卡带格式（`cart.toml`、`content/`、`content/python/`）和系统给的环境变量（`ALIA_CART_DIR`、`ALIA_SAVE_DIR`、`ALIA_SAVE_QUOTA_KB`、`ALIA_LANG`、`XDG_CACHE_HOME`）见 Alia Pad 的卡带文档。L4 的 VFS 不用自己挂载 `.acart`，只读 `$ALIA_CART_DIR`；引擎不能依赖主机路径和继承的环境变量。系统在沙箱里运行卡带，引擎不管沙箱 |
| 存档 | Alia Pad 卡带 SDK 的 `save.h`（只有头文件的 C API：原子写入、保留两个旧版本、配额；MIT，复制在 `third_party/alia-sdk/`），和 SDK 的 Python 版 `alia.save` 写同样的文件；目录是 `ALIA_SAVE_DIR`，卡带外面引擎用自己的目录（`api.md` §7） |
| 振动 | `SDL_RumbleGamepad`；马达硬件到货之前返回 False，不报错 |
| 声音 | SDL3 一个 48 kHz 立体声流，混音在引擎里（`api.md` §7）。系统的通知音播放时，系统把游戏的流渐变压低，播完恢复；游戏和引擎什么都不用做 |
| 生命周期 | `SIGTERM` 时退出。挂起不归游戏管（2026-10-29）：系统用 SIGSTOP 冻结卡带并显示"已暂停"；运行时只保证恢复时不追帧（两帧之间超过 0.25 s 的时间直接丢掉） |
| 宿主模式（E5，以后） | L1 的"宿主模式"：不创建窗口和上下文，宿主给一个已经绑定好的 FBO 和尺寸，引擎在里面画完就返回 |
| 屏幕旋转和 direct scanout | L3 最终 pass 直接按面板原生方向（竖屏 720×1280）输出，同时通过 SDL/Wayland 设置 buffer transform，sway 就能直接扫描输出，省掉一次合成。屏幕到货前按横屏 1280×720 输出 |
| 统计 | 引擎每秒在 stdout 打一行统计（帧时间、draw call、三角形……，`docs/stats-protocol.md`），任何工具都能读，超出 E2 实测的预算就可以标红 |
| 模拟器 | PC 版就是同一份代码；手柄来自真手柄或键盘 |

### 4.1 依赖关系

**编译时：引擎不依赖系统的任何代码，单独就能编译和运行**（PC、板子、CI 都一样）。从 SDK 复制进来的只有 `save.h`。

| 对方 | 方向 | 联系方式 | 引擎这边怎么处理 |
|---|---|---|---|
| 系统的手柄 | 引擎读 | 标准 SDL 手柄设备，不是代码依赖 | 有 SDL 映射就按位置读按键；没有，SDL 仍能当普通摇杆用 |
| `.acart` 卡带格式 | 引擎读 | 清单 `cart.toml`、环境变量，由 Alia Pad 的卡带文档定义 | 运行时读清单的 `[display]` 和标题；打包由 `tools/alia.py cart` 做（`docs/project.md`） |
| 卡带 SDK 的 `save.h` | 引擎包含 | 只有头文件的 C API，复制在 `third_party/alia-sdk/` | 存档直接用它 |
| 宿主应用（E5，以后） | **宿主依赖引擎**（反方向） | 以宿主模式链接 `libalia-engine` | 引擎提供稳定的宿主模式 C++ 接口和 pkg-config 文件 |
| 读统计的工具 | 工具读引擎的输出 | stdout 上的统计行 | 协议在本仓库定义（`docs/stats-protocol.md`） |
| MCU 固件 | 无关 | — | 引擎看不到 MCU |
| Megalith | 游戏依赖引擎 | Python 模块 `alia_engine` | 独立的游戏仓库，做成卡带；不放在引擎里 |

依赖方向总结：

```
游戏（Megalith 等） ──▶ alia-engine ──(头文件)──▶ 卡带 SDK 的 save.h
宿主应用（以后） ──(宿主模式)──▶ alia-engine
系统的手柄 ──(SDL 手柄，运行时)──▶ alia-engine 的 L1
```

和系统之间要同步维护的接口约定：卡带格式和环境变量（系统定义，引擎消费），以后的宿主模式接口（引擎定义，宿主消费）。都按版本号演进：接口变了就升主版本号，对方按版本适配。

## 5. 需要选择的地方

| # | 问题 | 选项 | 建议 |
|---|---|---|---|
| 1 | 图形接口 | (a) 直接写 GLES，不要抽象；(b) 薄 RHI，现在只有 GLES 后端，接口按"显式 pass、load/store 操作"设计，以后能加 Vulkan 1.0 后端；(c) 复用 StellarAlia 的 RHI | **(b)**。(a) 以后换 Vulkan 要大改；(c) 是 bindless 语义，GLES 实现不了。(b) 的额外成本很小，而且"显式 load/store"正好符合 tile GPU 的规矩 |

### 5.1 板上版本的交叉编译

- **为什么**：引擎依赖模板很重的库（EnTT、nanobind），在 4 核 A53 上编一次要几分钟以上；以后要在 CI 上编译。
- **编译器**：PC 上现成的 clang（23.x，`--target=aarch64-linux-gnu`）+ lld，不另装交叉编译器。
- **sysroot**：和板子完全一致的头文件和库，来自 Alia Pad 的 devkit，用 `ALIA_SYSROOT` 指定（不进 git）。这样链接的就是板子上的 glibc、libstdc++、SDL3、Mesa、Python 3.13，版本一定匹配。
  - 不用 Arch 的 `aarch64-linux-gnu-gcc`（16.x）：它带的 libstdc++ 比板子的新，产物会依赖板子上没有的符号版本。
- **工具链文件**：`cmake/aarch64-board.cmake`。
- **依赖分两类**：
  - **随引擎编译的库**（EnTT、glm、nanobind、Jolt、stb 等）：源码放 `third_party/`（或 CMake 按固定版本拉取），静态链接。新库默认都走这条路。
  - **板子系统提供的库**（glibc、libstdc++、SDL3、Mesa EGL/GLES、Python 3.13）：动态链接，来自 sysroot，必须和板子用同一份。这类库就是"板子操作系统的接口"，很少增加。
  - sysroot 对应板子的一个平台基线；引擎的每个发布版本声明自己针对哪个基线。
- **部署和测试**：`tools/board-deploy.sh [目标目录] [adb 设备]`：把测试用的编译结果经 adb 推到板子上，在板上跑全部测试，打印汇总。
- **后备**：可以在板上原生编译一次做交叉验证。

### 6.2 E2：板上实测预算（2026-10-29）

`alia-bench`（`apps/bench/`）：无窗口、关 vsync，每种负载跑 200 帧，最后等 GPU 做完，取平均。板子：FD702（Mesa 26.1.6，GLES 3.1），GPU 调频是 `simple_ondemand`（355–845 MHz），没有锁频，所以这是自动调频下的实际数字。输出 1280×720，内部 640×360，有雾，除非另外说明。

| 负载 | ms/帧 | 说明 |
|---|---|---|
| 空帧（天空 + 最终 pass） | 3.3 | 固定开销，主要是把 1280×720 写出去（约 3.7 MB）。1080p 电视输出 6.4 ms；竖屏 720×1280 旋转 3.3 ms，旋转不花钱 |
| 三角形：2 万 / 5 万 / 10 万 / 20 万 / 41 万 | 4.1 / 5.0 / 6.3 / 9.2 / 14.1 | 大约 26 ns/三角形，约 3800 万三角形/秒 |
| draw call：100 / 250 / 500 / 1000 次（每次 200 三角形） | 4.4 / 5.6 / 7.6 / 11.7 | 和同样三角形数的少量大网格比，每多一次 draw 约 +3 µs GPU；CPU 侧每个实例 8–15 µs（每次 draw 更新一次 UBO） |
| 填充：1 / 4 / 8 / 16 层全屏 @640×360 | 3.8 / 4.9 / 6.4 / 9.3 | 每层约 0.37 ms |
| 填充：1 / 4 / 8 层全屏 @1280×720 | 7.5 / 12.0 / 18.1 | 每层约 1.5 ms，是 640×360 的 4 倍 |
| 内部分辨率（5 万三角形）：640×360 / 854×480 / 960×540 / 1280×720 | 5.0 / 5.9 / 6.5 / 8.5 | |
| HUD 1000 个字符 | 3.5 | 几乎不花钱 |
| 类 Megalith（80 个小网格 + 2 层 + 120 字） | 4.6 | 实际的 Megalith 场景：78 个实例、约 1000 三角形 |

Python 侧（板上 Python 3.13）：`draw` 约 3.1 µs/次、`hud_rect` 1.2 µs、`hud_text` 1.7 µs、读输入 1.1 µs。Megalith 每帧 Python + 提交 **4.4 ms**（优化前 21 ms：rig 姿态每帧重复求值约 7 次，纯 Python 的 3×3 矩阵运算）。

**预算（60 Hz，16.6 ms）**，以后的游戏和功能按这个来：

- GPU：固定开销 3.3 ms，剩下约 13 ms。**三角形 ≤ 15 万/帧**（约 4 ms），**全屏层 ≤ 8 层 @640×360**（约 3 ms），**draw ≤ 300 次/帧**（CPU 侧约 3–4 ms）。三项不要同时用满。
- 内部分辨率：640×360 是默认；854×480 可以用（多约 1 ms）；1280×720 只给很轻的场景。
- CPU：游戏的 Python + 提交 **≤ 8 ms**（§1 的目标）。CPU 和 GPU 并行，帧时间约等于两者中较大的那个。
- 实例多了，先做的优化是**一帧一个 UBO 环形缓冲**和**同网格实例化**（早先的规划里就有），而不是减少游戏内容。
- **同网格实例化已经做了**（E4 第 6 步，2026-10-30）：不透明的实例按（网格、灯、贴地雾）分组，两个以上就一次 instanced draw 画一个分段，每个实例的变换、tint、fade 放在一个每帧的实例缓冲里；半透明的仍然逐个排序。黄金截图逐像素不变。板上 `alia-bench`（同一个小球网格）：100 个 4.57 → 4.34 ms，500 个 7.65 → 6.52 ms，1000 个 11.60 → 9.32 ms，megalith-like 4.68 → 4.46 ms。1000 个的时候剩下的基本是固定开销（3.3 ms）和三角形（20 万 × 约 26 ns）：每个实例的 draw 开销从约 3 µs 降到 1 µs 以下，粒子这种几个三角形的小网格最受益。
- **粒子**（E4 第 6 步，2026-10-30，板上无头，12 个三角形的网格粒子，会落地反弹）：同时活着 1000 个：模拟 0.11 ms，收集 + 剔除 + 提交 0.78 ms；2000 个：0.20 + 1.73 ms；4000 个：0.35 + 3.07 ms；8000 个：0.66 + 5.64 ms。也就是模拟约 85 ns / 个，画约 0.75 µs / 个（大头是 CPU 侧的收集和剔除，以后真需要再挪进实例缓冲）。预算：一帧同时 1000–2000 个粒子，花 1–2 ms。
- **声音**（E4 第 7 步，2026-10-30，板上作为卡带运行，屏幕亮着）：Megalith 的音乐和合成音效走引擎的混音器，`--demo` 带连射，测了 137 s：SDL 报 48000 Hz / 512 帧；`audio_late` 只有开头那 1 次（流启动），负载下 0 次断音；同时最多 3 个声音；游戏 61.6–62.0 fps、update 平均 3.95 ms，和没有声音时一样。普通优先级够用，不需要实时优先级。注意：系统 5 分钟没有手柄输入会关屏，关屏时合成器只给约 20 Hz 的帧，无人值守的跑分要先让屏幕保持亮。

待测：锁最高频（`performance` 调频要 root）下的上限、长时间运行的发热降频、GPU 时间戳（A702 是否支持 timer query）。

### 6.3 2D（E7，后期）

2026-10-28 决定：2D 和比赛游戏的移植**不是要紧的任务，排到 E6 之后**（早先的规划说"2D 要早做"，这里以本文为准）。在那之前，2D 只有 E1 的 HUD：按场景像素画矩形和 5×7 字体的文字，叠在 3D 之上。

#### 现状

| 有 | 没有 |
|---|---|
| HUD 矩形（带透明度）、5×7 文字（倍数缩放、阴影）；整数倍放大和黑边（最终 pass）；卡带清单的 `[display] render` 能选任意内部分辨率（比如 480×320） | 纹理和精灵；线、三角形、圆；裁剪；图层和排序；批量提交；不画天空的纯 2D 模式；中文字体 |

#### 借鉴 Unity 2D 的哪些东西

Unity 的 2D 是一组包（Sprite、Sprite Atlas、Tilemap、Pixel Perfect Camera、2D Animation、Sprite Shape、URP 2D 光照、Physics 2D 和 Unity UI）。对掌机有用的是它的**数据模型**，渲染方式不照搬：

| Unity 2D | 它怎么做 | 我们怎么做 |
|---|---|---|
| Sprite | 资源 = 纹理区域 + 轴心（pivot）+ 每单位像素数（PPU）+ 九宫格边距 | 同样的精灵描述：图集区域、轴心、九宫格边距（UI 面板）。像素游戏默认 1 单位 = 1 场景像素 |
| Sprite Atlas | 编辑器里打包，运行时按图集合批 | 图集在 PC 上烘焙（L4 打包工具，以后转成 ETC2）；运行时打包只作后备，给用代码画出来的精灵用 |
| SpriteRenderer + Sorting Layer / Order in Layer / Sorting Group / 透明排序轴 | 每个精灵常驻在场景里；排序键是"层 → 层内序号"，俯视游戏可以按 y 排序；一组精灵可以整体排序 | 排序键 = (层, 层内序号, 可选 y)；"组"让角色和它的武器、影子一起排序。和 Unity 一样**常驻**（见下文） |
| Tilemap（Grid、Tile、Rule Tile、TilemapRenderer 的 Chunk 模式、TilemapCollider2D） | 瓦片分块合成静态网格，只有改了的块才重建；规则瓦片在编辑时决定用哪张图；碰撞体从瓦片生成 | 分块静态顶点缓冲，脏块才重建；规则瓦片放在 PC 工具里，运行时不做；碰撞用瓦片标志（实心、单向平台、伤害）加查询函数 |
| Pixel Perfect Camera | 参考分辨率 + PPU，先渲染到低分辨率纹理再放大，相机对齐像素网格 | 已经是这个结构（内部分辨率 + 整数放大）。再加：相机和精灵位置取整到场景像素，避免像素游戏里的抖动 |
| Unity UI（Canvas，屏幕空间）和世界分开 | UI 不受相机影响，单独布局 | 2D 世界层用相机坐标，HUD/UI 层用屏幕像素；HUD 保持现在的接口，以后加九宫格面板 |
| 2D Animation（骨骼和蒙皮）、Sprite Shape | 骨骼动画、样条地形 | 先只做帧动画（帧列表加帧率）；骨骼 2D 以后可以复用 3D 的刚体 rig 思路；Sprite Shape 不做 |
| URP 2D 光照和阴影 | 2D 点光、法线贴图、阴影投射 | 不做（带宽）。2D 和 3D 共用 Look 调色和调色板，用调色代替光照 |
| Physics 2D（Box2D） | 刚体和碰撞体 | 先做 AABB、圆、瓦片碰撞的工具函数；Box2D v3（MIT）以后可选 |
| Sprite Mask、模板缓冲 | 遮罩 | 先用裁剪矩形，模板缓冲以后再说 |

#### 比 Unity 更适合我们的地方：以常驻对象为主

板上的 Python 很慢（§5 第 2 项），每帧一个物体调用一次的开销会随物体数增长。Unity 的精灵和瓦片地图是常驻组件，引擎每帧自己画，脚本只改变化的属性。我们也这样：

- **常驻**：精灵、精灵组和瓦片地图是引擎里的对象。Python 创建一次，以后只改位置、帧、可见性，或者改某个瓦片。**每帧的 Python 开销和"变化量"成正比，不和"物体数"成正比**。E4 有了 EnTT 以后，这些对象就对应 Sprite / Tilemap 组件。
- **即时**：线、矩形、圆、三角形、文字、单个精灵，每帧提交，画完就清空。用于 HUD、调试、小游戏。需要大量即时精灵时用批量接口（`draw_sprites(bytes)`：一个结构体数组，一次调用提交几百个）。
- **不做常驻画布**（2026-10-28）：它只对"不改写、直接搬比赛游戏"的兼容层有用，我们不急着快速验证，改写时增量绘制本来就要换成常驻对象。以后真要渲染到纹理（小地图、UI 缓存）再加，RHI 已经有渲染目标。

两种来源在 L3 合成同一份 2D 绘制列表：常驻对象先按排序键排好（只有变了才重排），即时内容按提交顺序跟在各层后面。

#### 渲染

- **仍然是一个场景 pass**（tile GPU 的规矩）。顺序：3D 场景（可以没有）→ 2D 世界层 → 叠色 → HUD/UI 层。纯 2D 游戏关掉天空，开始时用清屏色。
- 每帧的 2D 顶点放进一个动态缓冲，按"层 → 纹理 → 混合方式"合批，通常只要几次 draw；瓦片块是静态缓冲。
- 最近邻采样、坐标取整；精灵可以翻转、旋转、缩放、染色、设透明度。
- 字体：内置 5×7（已有）；以后加 BMFont/BDF 位图字体，中文用 FreeType 生成图集，常用字预烘焙。
- 测试：和 `test_handheld` 一样，做一张 2D 黄金截图。

#### 用比赛游戏验证（按适配难度从易到难）
